## The receipt list: what the rule reads vs what the writers write

The `posReceipts` read rule is:

```
  {
  allow read: if isAuthed() && (
  resource.data.sellerId == request.auth.uid || isAdmin()
  );
  allow write: if false; // CF-only
  }
```

| writer | path | writes `sellerId`? | writes `merchantId`? |
|---|---|---|---|
| `posCompleteCheckout (POS sale)` | functions/pos-zero-friction.js:360 | no | yes |
| `generateTrustReceipt (SOKONI Pay)` | functions/payment-trust.js:85 | no | yes |
| `M-Pesa checkout callback` | functions/index.js:7978 | no | yes |
| `RECEIPT async job` | functions/async-job-handlers.js:130 | **yes** | no |

Writers that can ever satisfy the gate: **1 of 4** — `RECEIPT async job`.

The three paths that actually produce merchant receipts — the POS sale, the SOKONI Pay
trust receipt, and the M-Pesa marketplace checkout — all write `merchantId` and no
`sellerId`. A merchant querying its own receipts from the browser is denied on every one
of them.

This is the **fifth** instance of *rules gating on a field nothing writes*, after
`shopEmployees.sellerUid`, `disputes.sellerUid`, `posCustomers.sellerId` and
`minishopAnalytics.ownerUid`. It differs from the other four in one way that makes it
worse rather than better: one writer *does* emit `sellerId`, so the rule is not visibly
dead. It returns a partial, silently incomplete list instead of an error.

So the honest classification for a merchant receipt list is **NEW AUTHORITY REQUIRED**,
not *SAFE (rules-scoped)*. The Firestore read is genuinely protected — it is just
protected against the merchant as well.

| `finosGenerateReceipt`<br><sub>finos-router.js</sub> | _assertAuth | SELF-scoped — receipt is written with buyerUid/generatedBy = auth.uid and emailed to the caller | **SAFE AFTER HARDENING** |

- **`generateTrustReceipt`** — The server decides. Recorded only because the ownership spelling is a third variant (`sellers/{id}.uid`) alongside `sellerUid` and `ownerId`.
- **`emailTrustReceipt`** — Any signed-in account can have any receipt emailed to any address it chooses. The mail body carries merchant name, line items, totals and customer name.
- **`voidTrustReceipt`** — Admin-only by design. Not a merchant authority.
- **`verifyTrustReceipt`** — This is the point of a trust receipt — a buyer verifies it without an account. It is NOT merchant authority and must not be used as one.
- **`sendPOSReceipt`** — No disclosure (nothing is read back), but any signed-in account can send SOKONI-branded receipt email/SMS with arbitrary contents to arbitrary recipients. Outbound-messaging abuse, not IDOR.
- **`posLogReprint`** — Audit integrity: reprint events can be attributed to a merchant the caller has nothing to do with, and any order's reprint counter can be incremented by anyone.
- **`finosGenerateReceipt`** — No cross-tenant exposure: a caller can only mint a receipt attributed to itself. But amounts/commission come from request.data with no transaction corroboration, so `receipts/` is not a trustworthy financial record. Not a merchant-list authority.
- **`posReceipts (client read)`** — See the writer table — the field the gate reads is not written by the paths that actually create merchant receipts.

## Is the tax authority account-scoped or shop-scoped?

**Account-scoped, and it introduces no new merchant identity.**

`etimsProfiles/{auth.uid}` uses the Firebase uid *directly as the document id*. It does not
resolve through `sellers/{id}`, `merchants/{id}`, `shops/{shopId}` or a claim. Every
merchant-facing eTIMS callable then derives `sellerUid` from `req.auth.uid` and queries
`etimsInvoices where sellerUid == uid` or checks `order.sellerUid === uid`.

That is the cleanest identity handling found in any census in this track: there is nothing
to converge and no legacy `merchants/{merchantId}` model to resurrect. The eTIMS path does
not need one and must not be given one.

The consequence to record — a limitation, not a defect — is that tax identity has **no shop
dimension**. A seller operating two shops has one KRA PIN, one invoice prefix and one
invoice sequence across both. That is very likely correct in Kenyan tax law (the PIN belongs
to the taxpayer, not the outlet), but it means a Merchant Tax surface must be labelled as an
**account-level** setting, not a per-shop one, or it will read as a bug the first time a
two-shop seller opens it.

By contrast the receipt side carries **three** merchant spellings — `merchantId` (POS and
M-Pesa receipts), `sellerId` (async job receipts and the rule), and `sellers/{id}.uid`
(`generateTrustReceipt`'s ownership proof). These are not yet established as an authority
conflict versus writer-specific representations; that determination belongs to the receipt
authority work, not to this census.

### What a Receipts/Tax stage could build on today

The entire **Tax** surface is available and server-decided: profile read/update/register,
PIN format check, seller stats, manual and bulk invoice generation, resubmission, and the
authorised HTML receipt download. That is a complete, coherent merchant Tax screen with
nothing to fix first — provided it is labelled account-level.

`generateTrustReceipt` is safe to call for issuing a receipt.

### What must not be built yet

- **A merchant receipt list.** There is no authority for it. Reading `posReceipts` from the
  client returns a silently partial list; adding a callable that accepts a `merchantId` would
  repeat the `posLookupCustomer` defect exactly.
- **Anything calling `emailTrustReceipt`, `sendPOSReceipt` or `posLogReprint`** until they are
  scoped. Binding them into Merchant would put a supported button on top of three open holes.
- **Receipt reprint counts or `receipts/` financial figures as displayed metrics** — both are
  writable by any caller, so showing them would violate the no-fabricated-metrics rule.

### Findings recorded for separate security stages, not fixed here

| # | finding | severity |
|---|---|---|
| 1 | `emailTrustReceipt` mails any receipt to any address for any signed-in caller | **high** — PII disclosure, IDOR on a guessable receipt number |
| 2 | `sendPOSReceipt` delivers arbitrary client-composed SOKONI-branded receipts to arbitrary recipients | **high** — brand spoofing + outbound-messaging abuse |
| 3 | `posLogReprint` accepts an uncorroborated `merchantId` and mutates any order's reprint counter | **medium** — audit integrity |
| 4 | `posGetQueueMetrics` (adjacent, same file) queries `posCheckoutMetrics` by a client-supplied `merchantId` with no ownership check | **medium** — cross-tenant read |
| 5 | `finosGenerateReceipt` mints a `receipts/` document with client-supplied amounts | **low** — self-scoped, but the collection is not a trustworthy record |
| 6 | `posReceipts` rule gates on `sellerId`; 3 of 4 writers emit `merchantId` | **medium** — silently partial reads |

Findings 1 and 2 are the same class as the already-fixed `posLookupCustomer` defect
(`9360cbd`) and the already-fixed `orderAdvance` defect (`1d49634`): authenticated was
treated as authorised. They are listed here and deliberately not fixed in a census stage.

### Queue impact

Receipts and Tax are not one screen and should not be sequenced as one. **Tax is ready
now**; **Receipts is blocked** behind a new authority plus three security fixes. Fulfilment /
Delivery remains ahead of both, per `docs/MERCHANT_2D2_QUEUE.md`.
