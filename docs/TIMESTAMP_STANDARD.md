# Timestamp Standard

**Status:** PERMANENT · platform-wide engineering standard
**Related:** [[PLATFORM_CONSTITUTION]] · [[Payments]] · [[Orders]] · [[Wallet]] · [[RELEASE_ACCEPTANCE]]

---

## The one rule

**A timestamp is the single source of truth for *when* an event happened, and it
is generated by a server — never by the user's device clock.** Store it in UTC
(ISO 8601 / Firestore `Timestamp`); convert to local time only for display; and
for audit/financial events, append a new timestamped record rather than
overwriting history.

```
2026-07-26T09:15:12.017Z
```

Device clocks are wrong, skewed, or forged. Any event used for money, inventory,
disputes, fraud detection, or reconciliation that trusts the device clock is a
defect, regardless of how correct it looks.

---

## How to generate a server timestamp on SOKONI

There are three contexts. Pick by *where the code runs*, not by how it reads.

| Where the write happens | Correct call | Why |
| --- | --- | --- |
| **Client (browser)** writing to Firestore | `serverTimestamp()` (modular) / `firebase.firestore.FieldValue.serverTimestamp()` (compat) | A sentinel Firestore resolves on **its** server at commit time. The browser never supplies the value. |
| **Cloud Function** (Admin SDK) | `FieldValue.serverTimestamp()` for the canonical event time; `Timestamp.now()` is acceptable | The function runs on Google's servers, so `Timestamp.now()`/`new Date()` are **already server time** — not a device clock. `serverTimestamp()` is still preferred for the *authoritative* event field because it is resolved at commit and is consistent across every field in the same write. |
| **Human-authored / passed across a boundary** (e.g. a value written into a log line, an event payload, an export) | `new Date().toISOString()` **on the server** | When you need a concrete string rather than a Firestore sentinel, generate it server-side in UTC ISO 8601. Never accept a timestamp string from the client for an audit field. |

**Key nuance that trips people up:** `new Date()` / `Date.now()` / `Timestamp.now()`
inside a **Cloud Function** is a *server* clock and is fine. The same calls in
**browser** code are the device clock and are not. When auditing, the file's
location (`functions/` vs root) decides which it is.

## Rules

1. **Server-generated, always** — for financial, inventory, order, delivery,
   wallet, auth, and admin/moderation events. If the write happens in the
   browser, use the `serverTimestamp()` sentinel; if it can happen offline or
   must be tamper-proof, route it through a Cloud Function.
2. **UTC ISO 8601 in storage.** Never store a local-time string as the record of
   truth. Firestore `Timestamp` is UTC by definition — prefer it.
3. **Local time only at the edge** — convert to the viewer's timezone when
   rendering, never when storing or comparing.
4. **Never overwrite history.** An event's timestamp is immutable. State
   transitions **append** (`createdAt`, `paidAt`, `deliveredAt`,
   `refundedAt`, …) — each a separate field or a separate audit-log row — so the
   full trail survives. `updatedAt` may be refreshed; the *event* timestamps may
   not.
5. **The device clock is display-only.** A browser `Date.now()` is fine for a UI
   countdown, an optimistic "just now", or a **localStorage** cache the server
   later reconciles. It must never be the value persisted as the authoritative
   event time.

## Event catalogue (authoritative time = server)

| Event | Field(s) | Written by |
| --- | --- | --- |
| Merchant account created | `createdAt` | Cloud Function / onboarding |
| Product uploaded | `createdAt` | client `serverTimestamp()` or CF |
| Inventory updated | `updatedAt` + movement row `at` | CF (stock is money-adjacent) |
| Customer placed order | `createdAt` | `checkout.html` → `serverTimestamp()` ✓ |
| Payment confirmed | `paidAt` / `processedAt` | CF (IntaSend webhook / verify) |
| Rider accepted delivery | `acceptedAt` | CF dispatch |
| Order delivered | `deliveredAt` | CF |
| Wallet withdrawal requested | `createdAt` | CF `functions/wallet.js` ✓ |
| Withdrawal completed | `completedAt` / `processedAt` | CF |
| Admin moderation action | `at` on an immutable `auditLogs` row | CF / admin path |

## Current compliance (audited 2026-07-26)

Not a rewrite — the platform is largely already here:

- **Core rails compliant.** Orders (`checkout.html`) write
  `createdAt: serverTimestamp()`. Wallet/payment mutations live in
  `functions/wallet.js` and run on the server clock. **236 client files** already
  use `serverTimestamp()`.
- **Cloud Functions are fine.** The large count of `Timestamp.now()`/`new Date()`
  in `functions/` is *server* time by definition, not the anti-pattern.
- **The gap is a long tail, mostly benign.** Browser `Date.now()` timestamps in
  bookings, commission/fee ledgers, and chama records are largely **localStorage
  caches** (`ledger.unshift`, `fees.push`) used for offline display, not the
  Firestore source of truth (`sokoni-pay.js` computes a `serverTimestamp()`
  sentinel for its Firestore writes). Each such path must be verified
  individually — presence of `Date.now()` in a file is **not** proof of a
  violation.

**Open remediation (needs per-path verification before any change):** confirm
that every *Firestore* write on a financial/audit path (commissions, fees,
bookings, direct `withdrawals.add`, admin promos/sales in `admin.html`) persists
`serverTimestamp()` and not the browser clock; convert the ones that don't.
Tracked, not yet done — see [[RELEASE_ACCEPTANCE]].

## Reviewer checklist

Before merging any code that persists an event:

- [ ] Does the authoritative time come from the **server** (sentinel or CF),
      not the browser?
- [ ] Is it stored as a Firestore `Timestamp` / UTC ISO 8601, not local time?
- [ ] Are state-change times **appended**, leaving prior timestamps intact?
- [ ] Is any `Date.now()`/`new Date()` in browser code display-only or a
      reconciled cache — never the persisted record of truth?
