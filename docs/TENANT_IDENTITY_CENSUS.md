## 2 · Verdicts

| relationship | verdict | basis |
|---|---|---|
| `merchantId` == `workspaceMemberships.businessId` | **PROVEN SAME** | `_assertBusinessPermission` resolves `businesses.doc(businessId)`; invitations are validated through the same helper before storing it |
| `merchantId` == `posStaff.merchantId` | **PROVEN SAME** | both written in the **same batch** by `createBusiness` |
| `merchantId` == `branchId` prefix | **PROVEN SAME** | `` branchId = `${merchantId}-main` `` |
| `shopId` == `sellers/{id}` | **PROVEN SAME** | both are the owner's uid |
| **`shopId` == `merchantId`** | **PROVEN DIFFERENT** | `merchantId` is generated by `_generateMerchantId()`; `shopId` is an auth uid. They cannot coincide |
| `businesses.businessId` field == `businesses` doc id | **PROVEN DIFFERENT** | the field is `'BIZ-…'`; the doc id is the merchantId |
| `shops/{uid}` ↔ `businesses/{merchantId}` link | **MISSING** | no code path writes a reference from one to the other |
| any given production employee's records across the three stores | **UNPROVEN** | requires data; no source path guarantees a `shopEmployees` record has a matching `workspaceMemberships` row |

**So there are exactly two tenant spaces, not three:**

```
OWNER-UID SPACE                    GENERATED-MERCHANT SPACE
  shops/{uid}                        businesses/{merchantId}
  sellers/{uid}                      workspaceMemberships.businessId
  shopEmployees.shopOwnerId          posStaff.merchantId + branchId
                                     posShifts (when opened by staff)
```

`businesses.businessId` (`BIZ-…`) belongs to neither — it is decorative.

## 3 · THE LIVE DEFECT — `sellerId` is polymorphic

`pos-staff-ops.js::_requireSeller` accepts `sellerId` and resolves it **two different ways
depending on who is calling**:

```js
if (auth.uid === sellerId) return sellerId;                      // OWNER  → sellerId is a UID
await _assertBusinessPermission(auth.uid, sellerId, 'pos');      // STAFF  → sellerId is a merchantId
```

The owner short-circuit never touches `businesses`, so it accepts a **uid**. The staff path
does `businesses.doc(sellerId)`, so it requires a **merchantId**. Both succeed. Both write.

**The same shop is therefore addressed by two different `sellerId` values depending on who is
acting**, and every record keyed on it inherits the split:

| collection | keyed by | consequence |
|---|---|---|
| `posShifts.sellerId` | whichever the caller passed | an owner's open shift and a staff member's open shift for the same shop are **invisible to each other**. `getCurrentShift` queries `sellerId + cashierUid`, so each sees only their own — masking the defect |
| `posApprovals.sellerId` | whichever the caller passed | **this breaks the approval loop just built** |
| `posRetailSales.sellerId` | `merchantId` from checkout | a third path again |

### Why this matters immediately

The cashier → manager loop (Priority 8) assumes both sides name the same shop:

- a **staff cashier** raises a request → `createApprovalRequest` stores `sellerId = merchantId`
- an **owner manager** opens the Sales Control Centre → `getPendingApprovals({ sellerId: uid })`
- `getPendingApprovals` filters `where('sellerId','==',sellerId)` → **finds nothing**

The manager sees an empty approvals list while a real request is pending. Nothing errors; the
request simply never appears. That is precisely the failure mode this programme treats as worse
than a crash — an accurate-looking screen that is silently wrong.

**Not reproduced against production**, because that needs two real accounts. It is derived from
the two resolution paths and the query, and it is falsifiable: if `getPendingApprovals` returns
a staff-raised request to an owner in production, this reading is wrong.

## 4 · What this means for convergence

The recommendation in [[EMPLOYEE_AUTHORITY_CONVERGENCE_DECISION]] survives, with one
correction: **converging employees is not the first step. Converging the tenant key is.**

`workspaceMemberships` is canonical *and already lives in the merchant space*. So the target is:

```
canonical tenant key = merchantId (the businesses/{…} doc id)
canonical employment  = workspaceMemberships (businessId == merchantId)
branch scope          = carried from posStaff as a field, not a second store
```

and the **owner-uid space becomes a compatibility surface** — `shops/{uid}`, `sellers/{uid}`
and `shopEmployees.shopOwnerId` resolved *through* a mapping to `merchantId`, never used as a
tenant key in new code.

The missing link is the blocker: **no code path connects `shops/{uid}` to
`businesses/{merchantId}`.** Building that resolver — owner uid → merchantId, via
`businesses where ownerId == uid` — is the first implementation step, and it is derivable from
existing data with no new store and no invented relationship.

## 5 · Fail-closed rule for the interim

Until the resolver exists and is proven, any new authorization **must not** accept a `sellerId`
that could be either space. It should take `merchantId` explicitly, or resolve the caller's
merchantId server-side from `businesses where ownerId == uid`, and **refuse** when the lookup
is ambiguous or empty — never fall back to treating a uid as a tenant key.

## 6 · Not proven here

- whether `_generateMerchantId()` has ever produced a value equal to a uid (inspection says it
