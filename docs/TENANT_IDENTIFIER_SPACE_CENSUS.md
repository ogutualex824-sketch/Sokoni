## 3. The critical checks, answered directly

- **One merchant with multiple shops?** No literal case (only 1 real `shops` doc exists), but the
  closer real analogue — **one owner with multiple `businesses` records** — is confirmed and live
  (§2, row above).
- **One business with multiple shop IDs?** Not observed (too few `shops` docs to test), but the
  merge history (`mergedFrom`/`retiredTo`) shows the *same commercial entity* has cycled through
  **three different merchantIds over time** (`SOK-E7J2Y8` → `D5Ql2EYr...`, with `SOK-GL58F7`
  separately still active for the same owner) — a related, real instability in the identifier over
  time even for one shop.
- **One shop under multiple merchant/business IDs?** Yes — KASS SHOP is reachable via `merchantId`
  `D5Ql2EYr...` (canonical, current) and `SOK-E7J2Y8` (retired but still has live `posStaff` and
  `posSettings` records pointing at it) and is *also* the owner of a wholly separate active
  business `SOK-GL58F7`.
- **Employees whose shopId differs from merchantId?** No real employee records exist to check
  (`shopEmployees` is empty). The one `workspaceMemberships` record's `uid` (`xrH21J5G...`,
  deprecated) differs from the canonical owner uid (`D5Ql2EYr...`) that its linked `businessId`
  (`SOK-GL58F7`) actually belongs to under current data — the closest real analogue, and it *does*
  disagree.
- **Payment/POS records using a different identifier than the shop authority?** Yes —
  `posSettings/SOK-E7J2Y8` and one `posStaff` record are both keyed to the retired merchantId, not
  the canonical `D5Ql2EYr...` one the shop authority (`shops`, `sellers`) uses.
- **Code that assumes equality without proving it?** `tenant-identity.js`'s own header comment does
  — *"`merchantId` is generated... so it can never equal an auth uid"* — and row 1 of the evidence
  table is a live, current production record where that is false.

## 4. Definitive result

```
shopId == businessId == merchantId?

VERDICT: DISTINCT identifier spaces, MAPPED in the common case via businesses.ownerId,
         NOT SAFE TO ASSUME EQUAL — with a confirmed live exception where the mapping
         collapses (merchantId literally equals the owner uid for one merged business)
         and confirmed live ambiguity (one owner, two simultaneously-active businesses).
```

This is not a clean fit for any single one of your five categories applied to the whole question —
the honest answer is genuinely mixed, and forcing it into one label would lose the finding that
matters most:

- **MAPPED** describes the *designed, intended* relationship: `businesses.ownerId` links a
  `merchantId` back to the `shops`/`sellers` uid space. This mapping is real and mostly holds (3 of
  4 `businesses` docs have a clean, generated `SOK-XXXXXX` merchantId distinct from any uid).
- **CONFLICTING** describes what actually happened once, in production, right now: a merge
  operation produced a canonical business record whose merchantId **is** the owner's uid — the
  exact thing `tenant-identity.js`'s own documentation says cannot happen.
- **DISTINCT** is the safe operating assumption going forward: nothing in this data supports
  treating `shopId`/`businessId`/`merchantId` as interchangeable, and `resolveMerchantIdForOwner`'s
  fail-closed, refuse-on-ambiguity design is validated by real data, not just defensive coding.

`branchId` (`${merchantId}-main`) and `posStaff` doc ids (`${branchId}-${uid}`) are confirmed
**DERIVED**, consistently, across all 4 real records — the one part of the model that holds up
exactly as documented.

## 5. Does this change the tenant-identity.js governance decision?

**Partially — it answers the one blocking data question, not the whole decision.**
`docs/EMPLOYEE_AUTHORITY_CONVERGENCE_DECISION.md` §6 Q1 asked exactly this question and marked it
"Blocking. Needs production data." That data now exists (§4 above) and confirms the decision
document's own working assumption was directionally correct — the spaces are not safe to converge
by assuming equality — while also surfacing a live data-quality issue (the uid-as-merchantId merge
artifact, the stale retired-business references in `posStaff`/`posSettings`) that document did not
anticipate. The other four questions in §6 (permission-vocabulary shape, whether `void` gets
`refunds` or a new `voids` permission, branch-scope requirements, dual-read window) remain pure
policy/product choices this census cannot answer and does not attempt to. **Not treated as
resolving the governance decision — only as removing its one data blocker.**

## 6. Does this change the `pos-staff-ops.js` cross-branch provenance track?

**No.** That finding (`docs/POS_STAFF_OPS_CROSS_BRANCH_PROVENANCE.md`) is about *which git history*
produced the code currently deployed — independent of whether the underlying identifier-space
model that code assumes turns out to be correct. This census makes the *model* question more
answerable; it says nothing about *where the deployed bytes came from*. That record stays open, on
its own track, exactly as before.
