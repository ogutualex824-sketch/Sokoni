# Merchant Devices / POS — Authority Census

**Stage 1 — read-only.** No UI changes, no repairs, no backfill, no deployment.

Generated by `scripts/census-devices-authority.js`. Every verdict was produced by
extracting the **full** function body and inspecting it. Re-run with:

```
node scripts/census-devices-authority.js --md > docs/MERCHANT_DEVICES_AUTHORITY.md
```

Fixture: `SELLER_A → SHOP_B → DEVICE_B`, and `SHOP_C → DEVICE_C` belonging to someone else.

## Headline

**POS device setup works, and it decides almost nothing.** Of the eleven callables that
read or write the POS device fleet, **9 authorise nobody** — and 8 of those contain no
ownership token of any kind: not a weak check, not the wrong check, none. The screen used
here is deliberately generous — it matches any of `permission-denied`, `ownerId`,
`adminUids`, `posStaff`, `isAdmin`, `sellerUid`, a `uid !==` comparison, or
`users/{uid}.merchantId` — which makes that result harder to reach, not easier.

The gap between the two numbers is `validateDeviceAccess`, which matches a token and still
authorises nothing. That is why the table below reports the screen and the hand-verified
answer in separate columns.

Exactly **one** merchant-facing callable in the fleet decides anything at all
(`registerDevice`), and it decides it against a record that does not name the merchant being
claimed.

So the answer to *"can a device be attached to the wrong shop?"* is **yes, trivially**, and
the answer to *"is POS setup the merchant authority?"* is **no**.

| callable | takes from the client | ownership token present? | does it actually decide? |
|---|---|---|---|

| `deviceHeartbeat`<br><sub>device-manager.js</sub> | deviceId | **none** | **NO** |
| `lockDevice`<br><sub>device-manager.js</sub> | deviceId | **none** | **NO** |
| `unlockDevice`<br><sub>device-manager.js</sub> | deviceId | **none** | **NO** |
| `remoteLogout`<br><sub>device-manager.js</sub> | deviceId | **none** | **NO** |
| `remoteUpdate`<br><sub>device-manager.js</sub> | deviceId + targetVersion | **none** | **NO** |
| `decommissionDevice`<br><sub>device-manager.js</sub> | deviceId | **none** | **NO** |
| `getDeviceList`<br><sub>device-manager.js</sub> | merchantId | **none** | **NO** |
| `bootstrapDevice`<br><sub>business-bootstrap.js</sub> | merchantId + branchId + deviceId | **none** | **NO** |
| `validateDeviceAccess`<br><sub>business-bootstrap.js</sub> | merchantId + branchId + pin | yes | **NO** |
| `adminGetPosDevices`<br><sub>admin-os.js</sub> | nothing | yes | yes — admin only |

The third column is a generous automated screen; the fourth is hand-verified. They
deliberately disagree in one place, and that disagreement is the reason the fourth column
exists: **`validateDeviceAccess` matches on `posStaff` and authorises nothing.** Its query is
`branchId` + `pinHash` + `status` — the client's `merchantId` is accepted and then never used
for authorisation. Given a correct staff PIN it returns the employee record for a branch the
caller has no relationship to. Rate-limited at 5 attempts per uid per 5 minutes, which bounds
a brute force without establishing who is asking.

`adminGetPosDevices` is admin-only and correct. `registerDevice` is the only merchant-facing
callable in the fleet that decides anything — and it decides it against the wrong record.

### 1. `bootstrapDevice` attaches any device to any merchant, and reactivates it

`bootstrapDevice` takes `merchantId`, `branchId` and `deviceId` from the caller, performs no
ownership check, returns the merchant's full configuration bundle, and then writes:

```js
db.collection('posDevices').doc(safeDeviceId).set({
  deviceId:   safeDeviceId,
  merchantId: safeMerchantId,   // client-supplied
  branchId:   safeBranchId,     // client-supplied
  cashierId:  uid,
  status:     'active',
}, { merge: true });
```

Three consequences, all computed above rather than inferred:

- device write present: **yes**
- writes `status: 'active'`: **yes**
- uses `{ merge: true }`: **yes**

So any authenticated account can (a) read any merchant's bootstrap bundle, (b) attach a new
device to any merchant, and (c) **re-point an existing device to a different merchant**,
because `merge: true` overwrites `merchantId` on a document that already exists.

And (d): `registerDevice` explicitly refuses to re-register a decommissioned device
(decommission guard present: **yes**), while `bootstrapDevice` writes
`status: 'active'` with no such check. **`bootstrapDevice` is a bypass of
`decommissionDevice`.** A device revoked by an administrator can bring itself back.

### 2. `registerDevice`'s staff branch proves the wrong thing

`registerDevice` does corroborate — it accepts the caller if they own
`businesses/{merchantId}` or `merchants/{merchantId}`, **or** if they are active `posStaff`.
That last query is:

- filtered by `branchId`: **yes**
- filtered by `merchantId`: **no**

Both ids come from the caller. A user who is legitimately staff at their own branch can
therefore send **their own `branchId`** together with **a victim's `merchantId`**: the staff
query succeeds against their own record, `staffSnap` is not empty, and the device is
registered under the victim's merchant. The staff record proves membership of a branch and
is never checked to belong to the merchant being claimed.

This is the same defect class as `orderAdvance` and `posLookupCustomer`: a real check that
validates something other than the thing being authorised.

### 3. The `posDevices` rule gates on a field the writers do not write

```
  {
  allow create: if claimsPosOwner();
  allow read:   if isPosOwner() || isAdmin();
  allow update: if isPosOwner() || isAdmin();
  allow delete: if isAdmin();
  }
```

`isPosOwner()` is `resource.data.sellerId == request.auth.uid`. The writers:

| writer | writes `sellerId`? |
|---|---|
| `registerDevice` | **no** |
| `bootstrapDevice` | **no** |

Both write `merchantId`. So the client-side rule for `posDevices` denies the merchant their
own device list — the **sixth** instance of *rules gating on a field nothing writes*, after
`shopEmployees.sellerUid`, `disputes.sellerUid`, `posCustomers.sellerId`,
`minishopAnalytics.ownerUid` and `posReceipts.sellerId`.

## Three device collections, three different things

The word "device" covers three unrelated registries. Conflating them is the first way a
Devices screen goes wrong.

| collection | what it actually is | key shape | verdict |
|---|---|---|---|
| `posDevices`<br><sub>device-manager.js + business-bootstrap.js</sub> | POS HARDWARE fleet — tills, terminals, printers attached to a branch | `posDevices/{client-supplied deviceId}` | **UNSAFE** |
| `userDevices`<br><sub>device-engine.js</sub> | ACCOUNT SESSION devices — where a person is signed in | `userDevices/{uid}_{deviceId} — the uid is IN the key` | **SAFE** |
| `securityDevices/{userId}/devices`<br><sub>security-identity.js + security-zero-trust.js</sub> | zero-trust device attestation | `securityDevices/{uid}/devices/{deviceId}` | **SAFE** |

`userDevices` is the model the POS fleet should have copied: the uid is **in the document
key**, the list query filters by the caller, and logout refuses another user's device.
Those three properties are asserted by this script's controls, not taken on trust.

A merchant Devices screen is about `posDevices`. `userDevices` belongs on a security/account
screen and must not be mixed in — "sign out my other phone" and "decommission till 2" are
different sentences with different blast radii.

- **`posRegisterPeripheral`** — A real check — and a FOURTH merchant identity spelling (`users/{uid}.merchantId`), alongside `businesses/{id}.ownerId`, `merchants/{id}.ownerId` and `shops/{id}.sellerUid`.

- **`posGetTerminalHealth`** — Queries peripherals and transactions by a terminalId the caller names. No merchant is established.
- **`posInitiateTerminalPayment`** — Starts a card payment on a terminal the caller names. Money path.

## What the merchant Devices screen does today

`merchant.html` already routes `devices` as `kind:'native'`, so there is no iframe to
remove. But the surface calls **no server authority at all**:

- reads `PrinterState`: **yes**
- calls any Cloud Function: **no**

It shows one live Web Bluetooth printer connection plus two "available in Cashier"
placeholders. The registered `posDevices` fleet — the tills a merchant actually owns — is
**invisible to its owner**, while being lockable and decommissionable by anyone.

That is the honest starting position: not a legacy island to convert, but a screen with no
server side yet, sitting above a registry that cannot safely be exposed as it stands.

## The fifteen questions, answered

| traced | finding |
|---|---|
| device registration | `registerDevice` (corroborates, imperfectly) and `bootstrapDevice` (does not corroborate at all). Two writers, one authority's worth of checking between them. |
| device ownership | Recorded as `merchantId` on the device document. Never verified on read or on any command. |
| active device | No concept of an "active device" per merchant. `status:'active'` is a device-level flag any caller can set via `bootstrapDevice`. |
| POS pairing | QR pairing IS token-gated — `_pairDevice` refuses on `b.pairingToken !== token`. This is the one part of the flow that holds. The token is regenerable by the owner. |
| printer configuration | `posPrinterConfig/{auth.uid}` — self-scoped and safe, but ACCOUNT-level: one printer config per account, not per device or per shop. |
| receipt printer / P58E | Entirely client-side (Web Bluetooth GATT held at shell level so it survives navigation). No server record, so it cannot be shown on another device or audited. |
| PDQ / terminal integration | `posGetTerminalHealth` and `posInitiateTerminalPayment` take a client `terminalId` with auth only. The second is a money path. |
| device removal / revocation | `decommissionDevice` — no ownership check, and bypassed by `bootstrapDevice` writing `status:'active'` with merge. |
| device status / heartbeat | `deviceHeartbeat` — no ownership check. Any caller can write heartbeat state for any deviceId. |
| branch / device relationships | `branchId` is namespaced as `{merchantId}-main` at bootstrap, which is good — but it is accepted from the client and never checked against the claimed merchant. |
| offline behaviour | Local caches (`bootstrapCache`, `syncQueue`, `pos-sync.js`). `syncQueue` rules are correctly `uid`-scoped; `bootstrapCache` is readable by any authenticated user. |
| employee / device permissions | `posStaff` membership is the staff path into `registerDevice`, and it is queried by `branchId` only — see defect 2. |
| can a device be attached to the wrong shop? | **Yes.** Two independent ways: `bootstrapDevice` (no check at all) and `registerDevice` (staff record not tied to the claimed merchant). |
| are device identifiers client-trusted? | **Yes, entirely.** `deviceId` is a client-generated UUID and is the document key. `registerDevice` validates it is a well-formed UUID v4 — which is a format check, not an ownership one. |
| device-local state | Six keys listed above, none of them authoritative and none of them audited. |


## Classification

| classification | capabilities |
|---|---|
| **SAFE** | `getPrinterConfig`, `setPrinterConfig`, `deviceRegister / deviceList / deviceLogout (userDevices)` |
| **SAFE AFTER HARDENING** | `registerDevice`, `posRegisterPeripheral` |
| **CLIENT-SCOPE / UNSAFE** | `deviceHeartbeat`, `lockDevice`, `unlockDevice`, `remoteLogout`, `remoteUpdate`, `decommissionDevice`, `getDeviceList`, `bootstrapDevice`, `validateDeviceAccess`, `posGetTerminalHealth`, `posInitiateTerminalPayment` |
| **BLOCKED** | `adminGetPosDevices` |
| **NEW AUTHORITY REQUIRED** | `posDevices client read (rules)`, `a merchant device fleet list` |
| **PUBLIC BY DESIGN** | — |

### Verdict for Stage 2

**Devices is BLOCKED. Do not build the UI on the existing POS device authorities.**

This is the case the instruction anticipated — POS setup works, and working is not the same
as deciding. A Devices screen built on `getDeviceList` + `lockDevice` + `decommissionDevice`
would put a supported merchant button on top of platform-wide device control.

What CAN be built now, and is genuinely useful on its own:

- **The local peripheral surface** — printer connect/test/forget, scanner and cash-drawer
  status. It touches no cross-tenant authority. This is what the screen already does, and it
  can be finished properly (P58E pairing state, reconnect, per-device naming) without any
  server change.
- **Printer configuration** via `getPrinterConfig`/`setPrinterConfig`, labelled
  **account-level** for the same reason Tax is — one config per account, not per device.

What must wait for a new authority:

- **The registered device fleet** (list, name, lock, unlock, decommission). Every one of
  those needs an owner check that does not exist, and the rule that would have scoped a
  client read gates on `sellerId`, which no writer writes.
- **Terminal / PDQ operations**, because the payment-initiating one is unscoped.

### Findings for separate security stages

| # | finding | severity |
|---|---|---|
| 1 | `bootstrapDevice` — no ownership check; returns any merchant's bootstrap bundle AND writes `posDevices` with client-supplied `merchantId`/`branchId`, `merge:true`, `status:'active'` | **critical** — cross-tenant config disclosure + device hijack + decommission bypass |
| 2 | `lockDevice`, `unlockDevice`, `remoteLogout`, `remoteUpdate`, `decommissionDevice`, `deviceHeartbeat` — auth only, client `deviceId` | **critical** — any account can disable any till on the platform |
| 3 | `getDeviceList` — auth only, client `merchantId` | **high** — cross-tenant device fleet disclosure |
| 4 | `registerDevice` — `posStaff` checked by `branchId`, never tied to the claimed `merchantId` | **high** — device attached to the wrong merchant |
| 5 | `posInitiateTerminalPayment` / `posGetTerminalHealth` — auth only, client `terminalId` | **high** — money path on a terminal the caller names |
| 6 | `posDevices` rule gates on `sellerId`; writers write `merchantId` | **medium** — sixth instance of the pattern |
| 7 | `validateDeviceAccess` — staff PIN checked against a client-supplied `branchId`, returning the employee record; the caller's relationship to that branch is never established | **high** — staff PIN oracle across branches |

Finding 2 deserves a note on blast radius: `decommissionDevice` is not reversible by
`registerDevice`, which refuses decommissioned devices. An attacker can therefore take a
merchant's till out of service through the documented path, and the documented recovery path
refuses to bring it back.

### Identity, recorded not fixed

The device path introduces merchant identity spellings this track has not yet reconciled:
`businesses/{id}.ownerId`, `merchants/{id}.ownerId`/`adminUids`, and
`users/{uid}.merchantId` — none of which is `shops/{shopId}.sellerUid`. Per the standing
instruction, this census does not resurrect `merchants/{merchantId}` to make a legacy path
convenient, and does not "fix" the spellings on aesthetic grounds. Whether they are
writer-specific representations or a genuine authority conflict is a question for the
identity work, not for Devices.
